一、项目概览

1.1 项目简介

《元素战机》是一款基于 Unity 2022.3 开发的 2D 俯视角弹幕射击游戏。玩家操纵一架战机在大地图上移动，自动向当前朝向持续开火，通过击杀敌人积累经验、在升级时三选一强化属性，并在五个元素属性（火、冰、水、雷、岩）之间自由切换，利用属性克制与元素反应对抗三波杂兵与关底 Boss。

游戏的设计重点落在两件事上：一是"元素"不是单纯的换皮伤害类型，而是贯穿弹道形态、大招表现、克制倍率与机制联动的完整系统；二是把"刷一把就走"的街机手感与"跨关继承成长"的养成感结合起来，让每一关都既有即时的爽感，也有长期的推进目标。

项目从一个空白工程起步，全部玩法、界面与表现均由自行编写的 C# 代码驱动，未使用任何第三方玩法框架。

1.3 核心玩法循环

单局游戏的流程可以拆成一条清晰的闭环：进入关卡后，波次系统按时间轴刷出三波杂兵；击杀杂兵获得经验与能量，经验满即触发升级三选一，能量满即可以释放元素大招；三波清空后触发全屏警告，Boss 登场；击败 Boss 后结算，本局的成长数值按规则写入永久存档，下一关随之解锁。若中途阵亡，本局收益作废并回到结算界面。

这条闭环里有两个节奏控制点。第一个是升级三选一：它会将全局时间流速降至 0.4 倍，给玩家一个短暂的决策窗口，避免在弹幕中手忙脚乱。第二个是 Boss 登场前的 2.5 秒冻结：把 timeScale 直接设为 0，配合全屏红色覆盖层，把"危险即将到来"这件事做成一个强提示。

2.3 模块间通信机制

项目并存四种通信方式，按耦合强度从弱到强排列，实际使用时按场景选择。

  • C# 事件：用于"一件事发生，多方关心"的场合。GameManager.OnEnemyKilled 由波次系统订阅以维护存活计数；WaveSpawner.OnAllWavesCleared 由关卡管理器订阅以触发 Boss。订阅前一律先解绑再绑定，避免场景重载导致回调重复执行。
  • 静态类：所有纯数据与纯工具都做成静态类，例如 LevelConfig、ElementDatabase、SaveSystem。这类代码没有生命周期、没有状态残留，调用方不需要持有引用，是项目里最轻的一种依赖。
  • 单例：GameManager、LevelManager、UIManager、HUD 等需要被全局访问的管理者采用 Instance 单例，在 Awake 中直接赋值。单例只用于"全剧唯一"的对象，不滥用到实体上。
  • Inspector 引用：六个传统面板的控件字段通过编辑器拖拽绑定，配合 UILayoutBuilder 一键生成并自动连线，避免手工拖错。

这里有一个设计取舍值得说明：没有引入依赖注入容器，也没有做服务定位器，因为项目规模只有四十个脚本，过度抽象反而增加阅读成本。真正需要解耦的热点（击杀事件、波次事件）用 C# 事件处理，其余直接用单例，是复杂度与可读性的平衡点。

2.4 主循环：固定步长设计

游戏逻辑没有直接跑在 Update 上，而是用累加器推进固定步长。GameManager.Update 记录帧间隔，以六十分之一秒为一步，单帧最多补五次，防止卡顿后出现"补帧雪崩"。

固定步长带来两个直接收益。第一，弹幕密度、移动速度、技能节奏全部与帧率解耦，120Hz 屏幕与 60Hz 屏幕上的手感完全一致。第二，逻辑帧可预测，调试时能按帧数精确复现问题。

代价是输入采集必须单独处理。Input.GetKeyDown 只在真实帧有效，而高刷新率下某些真实帧并不会执行逻辑步，那一帧按下的键会被直接丢掉，表现为"按大招偶尔没反应"。解决方案是在真实帧把按键写进三个待处理标志位，在逻辑步里消费并清零；非游戏状态时主动清空标志位，防止暂停期间按下的键在恢复后突然生效。

三、核心系统实现

3.1 玩家控制

移动采用加速度与减速度双参数模型，而不是直接赋值速度。按下方向键时以加速度逼近目标速度，松开时以更大的减速度回落，手感上"起步略缓、刹车干脆"。速度上限由跨关成长决定，避免后期出现瞬移感。

射击是全自动的，射击间隔由攻速等级换算成帧数，最低限制为两帧，防止后期攻速堆叠导致单帧生成过多子弹。弹道数量随成长增加，以扇形或平行阵列排布。

受击判定分为三态：无敌帧、护盾抵扣、正常掉血。护盾优先消耗，无敌帧期间忽略一切伤害来源，掉血后触发震屏与低血渐晕。三种状态的优先级写在一个函数里，避免多处判断产生歧义。

3.2 元素系统与属性克制

元素表是静态数据，每个元素记录名称、代表色、贴图文件名、伤害倍率与反应规则。克制关系用一个二维倍率表表达，查表即可得到伤害系数，新增元素只需要在表里加一行一列，不需要改动战斗代码。

同属性攻击会被判定为免疫，这是刻意设计的负反馈：玩家不能一把武器打到底，必须根据敌人属性切换。当两个相克属性相遇时触发元素反应，反应不只是数字变化，还会施加实际状态：冻结让目标停止行动若干帧，超载造成击退，融化与超导施加减速。命中给两点能量，触发反应额外给五点，这条规则实际上在鼓励玩家主动去打克制，而不是站桩输出。

3.3 碰撞与伤害结算

项目完全没有使用 Unity 的物理系统，没有 Collider，也没有 Rigidbody，所有碰撞由自研的轴对齐包围盒判定完成：取两个矩形中心距与半宽半高之和比较，相交即命中。这样做的原因有三个：弹幕数量大时物理引擎的开销不划算；需要精确控制判定框尺寸以贴合像素风美术；伤害结算要与元素倍率、反应、能量一并处理，走物理回调反而绕远。

碰撞检测每逻辑步执行一次，分四组：玩家子弹对敌人、玩家子弹对 Boss、敌方子弹对玩家、敌人本体对玩家。每组内部是朴素的双重循环，靠每帧清理死亡实体来控制列表规模。在当前的敌人数量级下，这个复杂度可以接受；如果后续要上大规模弹幕，这里是最先需要改成空间划分的地方，我在文档第九节把它列为已知优化项。

3.4 敌人与波次

杂兵的生成点不在屏幕内，而是按玩家当前视野外的一圈随机取点，保证"敌人从外面飞进来"的观感，而不是凭空出现在画面中央。

波次系统跑三轮，每一轮的结束条件是两个条件的与：持续时间到，且场上存活敌人清零。开局时按比例先铺一批敌人，避免出现开局几秒无事可做的空窗。三波结束后抛出清场事件，关卡管理器接住后进入 Boss 流程。

敌人的成长与玩家同步：血量按通关次数递增约三成五，伤害递增约一成八并设上限，而移动速度不参与跨关成长。最后这一条是刻意为之——玩家移速有硬上限，如果敌人还能继续加速，后期会变成无法躲避的必死局面，难度曲线会直接崩掉。

3.5 Boss 三阶段状态机

Boss 的生命周期用一个显式阶段枚举管理：入场、一阶段、二阶段、三阶段、死亡。入场阶段从活动区上边缘滑入，期间不攻击，给玩家一个准备窗口。血量降到六成与三成时切换阶段，切换的不仅是数值，还包括弹幕密度与技能类型。

Boss 的攻击节奏是"一轮环形弹幕、一轮专属技能"交替。这里有一个容易被忽略的细节：如果 Boss 在某一阶段被瞬间打掉大量血量，可能直接跳过技能阶段，玩家就永远见不到这个 Boss 的技能。为此在十分之一血处加了一次强制技能释放，保证每个 Boss 的核心招式至少登场一次。

3.6 Boss 技能的模板方法

四个专属技能（熔岩喷柱、海底漩涡、落雷、岩石突刺）共享同一套三段式生命周期，因此抽象出一个基类统一骨架，子类只覆写其中一段。

阶段帧数表现
预警60半透明正弦闪烁，提示"这里即将出事"
生效45 至 360（各技能不同）伤害判定与视觉表现
消散24线性淡出后销毁

这套结构把"什么时候危险、危险多久、什么时候结束"变成统一的时间契约，玩家在不同技能之间能建立一致的阅读习惯。子类只需要实现生效期的行为，新增技能不需要重复写预警与消散逻辑。

元素克制在这里被延伸到了机制层：火柱命中会附加三秒灼烧，而水属性大招释放的瞬间会熄灭场上所有火系召唤物并清除自身灼烧。也就是说元素关系不只体现在伤害数字上，还体现在"能不能解掉对方留下的场地效果"。

3.7 升级三选一

升级效果用委托承载：每张卡片持有一个 Action，点击即执行。这样升级池可以自由组合增益，不需要为每一种组合写一个类。卡片有 3 秒倒计时，超时自动选择第一项，防止玩家在减速状态下无限停留。

前两次升级有保底，必定出现"解锁新元素"的选项，保证新手在一局内就能体验到属性切换这一核心机制。

3.8 跨关成长与数值平衡

永久成长有六条线：生命、攻击、弹道数、攻速、移速、能量上限，每一条都有硬上限。上限不是拍脑袋定的，而是从"最坏情况"反推：弹道数封顶五条，是因为再高屏幕就会被弹幕铺满、玩家看不清敌人；移速封顶九级，是因为再快就会穿模般地掠过地图；攻速封顶八级，配合两帧最小间隔刚好不产生性能问题。

所有写入都经过钳制，读档时也钳制一次，防止旧存档或手改存档带来越界数值。

3.9 道具与彩蛋

局内道具共六种，掉落权重不同，拾取后进入漂浮与磁吸状态，靠近玩家时加速吸附。道具效果包括回复、增伤、护盾等，全部通过统一的效果入口分发。

彩蛋是一个独立实体，固定在活动区右下角，不注册进敌人列表，因此玩家子弹会直接穿过它、不会造成伤害。玩家靠近到一定半径内，它会从道具池中洗牌取三个不重复的道具散落在周围。每关一次，关卡结束时统一清理。这个设计的目的很单纯：给紧张的弹幕节奏留一个喘气点，同时让地图探索有一点正向反馈。

四、界面与美术的技术方案

4.1 全代码生成战斗界面

战斗 HUD 没有使用任何 Prefab，也没有放在场景里，而是在 HUD.BuildUI 中完全由代码构建：创建独立 Canvas、设置排序层、逐个生成面板与控件、绑定事件。这样做的好处是界面与逻辑同源，改布局只改一处代码；坏处是所有坐标都要手算。

为此项目封装了一个统一的定位函数，把"锚点、轴心、偏移、尺寸"四个参数收口。同时定下一条纪律：贴边的元素一律用边角锚点，绝不写死绝对坐标。原因是 Canvas 参考分辨率设为 1024×768 且宽高匹配系数取 0.5，当实际窗口是 16:9 时，逻辑宽度会变成约 1180 而不是 1024，写死坐标的控件会直接飞出屏幕。

4.2 程序化贴图生成

血条底框、能量条、护盾点、光环、敌人子弹、九宫格面板这些元素如果全部依赖美术出图，既拖进度也难统一风格。项目写了一个贴图工厂，逐像素填充 Texture2D 再转成 Sprite，用一套代码生成整套 UI 素材。

几个实现要点：渐变条采用上亮下暗加顶部高光带的做法，生成时用白色，实际使用时靠 Image.color 染色，一套纹理就能出多种颜色；柔光环用"距环半径的距离"做出平滑衰减，中心再叠一层淡光；九宫格框必须使用 SpriteMeshType.FullRect，否则默认的 Tight 模式会按 alpha 裁剪网格，九宫格拉伸后会出现破面。另外 Sprite.border 是只读属性，只能在 Sprite.Create 的重载里以参数形式传入，事后赋值无效。

低血渐晕也是同理，用径向渐变生成"边缘暗红、中心透明"的贴图，血量低于三成时按脉搏节奏脉动。

4.3 中文字体与行高陷阱

这是整个项目里排查时间最长的一个问题，值得单独记录。

症状是：Boss 血条上方的名字底板存在，颜色、层级都正常，但底板里没有文字。最初怀疑是字体缺字、层级遮挡、颜色错误，全部排除。

真正的原因在行高。所用中文字体的行高约为字号的一点四五倍，而 Unity 的 Text 组件默认垂直溢出模式是截断。当控件矩形高度小于行高时，Unity 不是裁掉一半，而是整行文字直接不渲染。Boss 名用 20 像素字号，控件高度 26 像素，行高需要 29 像素，差了三像素，于是整行消失。

修复分两步：第一步在统一的文本创建函数里把垂直溢出改成溢出，一处修改解决全局；第二步单独排查那些高度仍然偏小的控件，逐个调整尺寸。同时定下一条项目规范：所有运行时生成的文本，控件高度至少给字号的一点五倍。为了让文字压在亮色背景上依然可读，所有文本统一加黑色描边。

字体本身做了三级回退：主字体思源黑体，缺失时退到像素体，再缺则退到 Unity 内置字体。这样即使打包时漏了字体资源，界面也不会变成一片空白。

4.4 小地图逐像素渲染

小地图是一张 140×140 的运行时纹理，每帧全量上传像素会产生可观开销。项目采用双缓冲：一张基底图预先烘焙好背景、网格线与边框，刷新时先整块拷贝基底，再在上面画敌人点、Boss 点、玩家点与相机视野框，最后一次性上传。

同时把刷新频率限制在约每秒十二帧，用非缩放时间驱动，保证暂停时小地图仍然跟随鼠标与动效更新，但不会因为每帧重绘而掉帧。

4.5 反馈层设计

打击反馈由四件事叠加完成：命中闪白、震屏、飘字、音效。震屏幅度按伤害量分级，飘字走抛物线并在后半段淡出，音效按类型分池播放。这些都不在战斗逻辑里直接调用，而是由事件驱动，表现层订阅后各自演出，逻辑层不关心表现细节。

五、数据与存档

5.1 存档结构

存档以 JSON 形式写在应用数据目录下，内容包含最高分、排行榜、关卡解锁进度、元素解锁状态、图鉴收集计数、跨关成长数值。

5.2 序列化方案

Unity 内置的 JSON 工具不支持字典，而图鉴需要"敌人类型到击杀数"的映射。项目的做法是用键值对列表模拟字典：定义一个包含键与计数的结构体，序列化为数组，读取时遍历成字典使用。这样既保住了内置序列化的零依赖，又满足了字典语义。

读档做了两层防御：逐字段判空并给默认值，外层再包一层异常捕获，遇到损坏的存档直接回退到新档，而不是让游戏卡在启动阶段。

5.3 首次通关判定的顺序问题

跨关成长只在"首次通关"时写入，反复刷同一关不能刷属性。这条规则本身简单，但实现顺序极易出错，踩过一次坑。

正确的顺序是三步：先判断本关是否已通关，再结算并提交成长，最后才解锁下一关。如果把解锁放在最前面，判定时最大已解锁关卡已经加一，本关永远会被认为"已经通过"，成长就永远不会提交。同理，提交成长必须早于关卡的结束清理，否则玩家对象被回收，属性已经取不到。

阵亡、中途退出、按 Esc 返回菜单这三种情况都不写入任何成长，本关收益作废。这条规则写在关卡管理器的统一出口里，而不是分散在各个分支上。

七、工程化与工具链

7.1 资源导入自动化

图片导入设置原本需要逐张手动指定类型、网格模式、轴心，一次导入几十张图时极易漏配。项目写了一个资源后处理器，监听导入流程，凡是位于指定目录下的图片，自动按精灵、单图、全矩形、居中的规则设置。新增美术资源只要丢进目录，导入参数自动正确。

7.2 界面骨架一键生成

六个传统面板涉及上百个控件与字段引用，手工搭建既慢又容易连错。编辑器扩展提供了一个菜单项，一键生成八个面板对象并自动完成字段连线，生成后仍可自由修改。这把"搭骨架"的时间从数小时压缩到几秒，且不会出现漏连导致的空引用。

7.3 命令行构建与打包

项目使用 Unity 批处理模式完成自动构建：指定工程路径、输出路径与日志路径，无界面执行，构建完成后直接产出可执行文件与数据目录。构建过程不依赖人工点击，便于反复出包与回归验证。

这里遇到过一个环境问题：图形界面关闭后直接调用编辑器，进程会立即返回，日志停在许可握手阶段，看起来像构建失败。实际原因是编辑器进程切换导致父进程提前退出。解决办法是启动后轮询进程状态，等待真正退出再读日志与产物，而不是依赖返回值。

9.2 后续计划

第一优先级是性能：把子弹、特效、飘字迁入对象池，把碰撞改为网格空间划分，这两项完成后可支撑数倍于现在的弹幕密度。

第二优先级是把硬编码的关卡表迁移到 ScriptableObject，让数值配置脱离代码，策划可以直接在编辑器里调参并即时预览。

第三优先级是表现补齐：为五种元素敌人制作独立受击动画，补充背景音乐与更丰富的打击音效，并针对不同分辨率做一次系统性的自适应验证。

交互层面计划补上触屏与手柄支持，同时统一梳理一遍文字与背景的对比度，把登录页与结算页的可读性问题解决掉。
